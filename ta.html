IC151 · For teaching assistants

TA manual

Everything you need to run a lab. You do not need a laptop, command line tools, or admin rights — all of it works from the GitHub app on your phone.

How access works

Read this once. Almost every problem a student brings you comes from this being misunderstood.

  • Each student has their own private team in the organization.
  • They receive one invitation email, at their institute address, near the start of the course. They accept it once, ever.
  • Every assignment repository is attached to their team. Once they have accepted, new assignments appear instantly — there is nothing further to accept, no second email, no per-assignment invitation.
A student who never accepted that first email can open nothing, all semester. This is by far the most common cause of “I get a 404”. Check it before anything else.

Access does not depend on the GitHub username they wrote on the registration form. A typo there no longer blocks anything.

The two things you do here

Both are GitHub issues in the private course-admin repository. If these links show a 404, your GitHub account has not been added yet — ask the instructor.

  • Release an assignment to a batch
  • Report a student who cannot get in

Everything else — writing assignments, sending invitations, changing who has access — is done by the instructor.

Releasing before your lab

Each student gets their own private repository, created from the assignment template and attached to their team. They do not exist until someone releases the batch, so do this before your lab starts, not during it.

  • 1 Open Release an assignment to a batch.
  • 2 Type the assignment id exactly as the instructor announced it, for example helloworld. Pick your batch. Submit.
  • 3 Wait about a minute. A bot replies with a dry run — what it would do. Nothing has been created yet.
  • 4 If the numbers look right, add the go label to the issue. On a phone that is two taps — see below.
  • 5 The bot creates the repositories, attaches each to its student team, and closes the issue.

Replying /apply as a comment does exactly the same thing. The label exists because it is far easier to tap than to type on a phone.

Adding the go label

Removing the go label afterwards does nothing — the release has already happened. To release a different batch, open a new issue.

Re-running a release is always safe. It never recreates, resets, or overwrites a repository that already exists, and it never touches student work. It only fills in what is missing. If you are unsure whether a batch was released, just release it again.

Reading the bot's reply

The reply counts students in each state. A dry run shows the first two; the go label shows the rest.

  • would_createThe repository does not exist yet and will be created when you reply /apply. On a first release this is normally the whole batch.
  • would_attachThe repository already exists; only the team attachment is missing. Normal when you re-run a release.
  • activeDone. The student accepted their invitation and can push to their repository right now.
  • pending_acceptanceThe repository is ready and correctly attached, but the student has not accepted their organization invitation yet, so they will still see a 404. Nothing is broken and there is nothing to re-run — the student has to accept. Tell them to check their institute email.
  • team_missingThat student has no team. Tell the instructor; they need to be set up and invited.
  • needs_reviewA repository exists that our records do not know about. Stop and tell the instructor — do not re-run to try to fix it.
  • UNEXPECTEDAn account that is not that student can reach their repository. Treat this as an access incident and tell the instructor immediately.
  • errorGitHub refused something. Re-running usually clears a temporary failure. If the same student errors twice, tell the instructor.

A large pending_acceptance count early in the course is normal and is not a failure. It shrinks as students accept.

“I get a 404 on my repository”

GitHub shows the same 404 whether a repository does not exist or the student simply cannot see it. Work down this list in order rather than guessing. Ask for their roll number first.

  • Invitation never accepted. The most common cause by far. Have them search their institute email for a GitHub invitation, or open github.com/notifications while signed in. Accepting it fixes every assignment at once, not just this one.
  • Signed into the wrong account. Check the avatar in the top-right on github.com. Students with a personal account and an institute account very often land on the wrong one. The invitation was sent to their institute address, so it must be accepted by whichever account they intend to use all semester.
  • Batch not released yet. Confirm which lab batch they are actually in. Nothing to fix — the link 404s until the batch is released.
  • Invitation never arrived. If they have no invitation email at all, their address may be wrong in our records. Report it.
  • Accepted with an account they no longer want to use. Report it — switching accounts changes who can reach their work, so only the instructor can do it.
A wrong GitHub username on the registration form no longer breaks access. Access follows the invitation sent to their institute email, not the username they typed. If a student is worried they mistyped it, that alone is not the problem — keep working down this list.

Reporting a student who cannot get in

Only the instructor can change who reaches a repository. Opening the report is the escalation — you do not need to message anyone separately.

  • Give the roll number exactly as the student writes it, including any leading zeroes.
  • Say what you already checked. “Has no invitation email at all” and “accepted but still 404” lead to completely different fixes.
  • Use “someone else has access” only for a genuine access incident — it is handled first, ahead of everything else.
  • One report per student, so each can be tracked separately.

What the tooling will never do

  • It will never delete, rename, archive, or make a repository public.
  • It will never reset or overwrite work a student has already pushed.
  • It will never grant access to anyone outside the student's own team.
  • It will never accept an invitation on a student's behalf.

This is why re-running a release is safe, and why a student who has not accepted their invitation has to accept it themselves.
