IC151 · For teaching assistants

TA manual

Everything you need to run a lab. You do not need a laptop, command line tools, or admin rights — all of it works from the GitHub app on your phone.

The two things you do here

Both are GitHub issues in the private course-admin repository. If these links show a 404, your GitHub account has not been added yet — ask the instructor.

  • Release an assignment to a batch
  • Report a wrong GitHub username

Everything else — writing assignments, fixing usernames, changing who has access — is done by the instructor. You never need to touch repository permissions yourself.

Releasing before your lab

Each student gets their own private repository, created from the assignment template. They do not exist until someone releases the batch, so do this before your lab starts, not during it.

  • 1 Open Release an assignment to a batch.
  • 2 Type the assignment id exactly as the instructor announced it, for example helloworld. Pick your batch. Submit.
  • 3 Wait about a minute. A bot replies with a dry run — a count of what it would do. Nothing has been created yet.
  • 4 If the numbers look right, reply with /apply as a comment.
  • 5 The bot creates the repositories, records what it did, and closes the issue.
Re-running a release is always safe. It never recreates, resets, or overwrites a repository that already exists, and it never touches student work. It only fills in what is missing. If you are unsure whether a batch was released, just release it again.

Reading the bot's reply

The reply is a count of students in each state. On a dry run you will see the first two; after /apply you see the rest.

  • would_createA repository that does not exist yet and will be created when you reply /apply. On a first release this should be nearly everyone in the batch.
  • would_grantThe repository already exists; only the student's access will be added. Normal when you re-run a release.
  • pushDone. The student has accepted the organization invitation and can write to their repository right now.
  • invitedDone on our side. The repository exists and an invitation has been sent, but the student has not accepted it yet. Until they do, they will see a 404. This is expected and needs no action from you.
  • pending_usernameThe student has not given a valid GitHub username, so there is nobody to grant access to. Their repository is still created. Release the batch anyway, then file a username report for each one.
  • needs_reviewA repository exists that our records do not know about. Stop and tell the instructor — do not re-run to try to fix it.
  • errorGitHub refused something. Re-running usually clears a temporary failure. If the same student errors twice, tell the instructor.

A large invited or pending_username count on a first release is normal and is not a failure.

“I get a 404 on my repository”

GitHub shows the same 404 whether a repository does not exist or the student simply cannot see it. So work down this list in order rather than guessing. Ask them for their roll number and the GitHub username they submitted.

  • Signed into the wrong account. Check the avatar in the top-right on github.com. Students with a personal account and an institute account very often land on the wrong one. Sign out, sign back in with the registered account.
  • Invitation not accepted. Have them open github.com/notifications or search their email for the GitHub invitation. This is the single most common cause.
  • Batch not released yet. Confirm which lab batch they are actually in. Nothing to fix — the link 404s until the batch is released.
  • Username does not exist on GitHub. Open github.com/<username>. If it is a 404, the username is wrong or the account was never created. File a username report.
  • The profile is clearly somebody else. File a username report immediately and mark it as an access incident. A stranger may have write access to that student's repository.
The student fixes their own username. They re-submit the registration form with the correct username — same form, same email address, no need for a new one. The latest response replaces the earlier one. Then their access is corrected on the next update.

Reporting a wrong username

Only the instructor can change a username mapping, because doing so changes who can reach a private repository. Opening the report is the escalation — you do not need to message anyone separately.

  • Give the roll number exactly as the student writes it, including any leading zeroes.
  • Only fill in a corrected username if the student told you what it is. Never guess one on their behalf, and never look one up and assume.
  • Use “belongs to someone else” when the profile is plainly not the student. That is treated as an access incident and handled first.
  • One report per student. If several students in your lab are affected, file them separately so each can be tracked.

What the tooling will never do

  • It will never delete, rename, archive, or make a repository public.
  • It will never reset or overwrite work a student has already pushed.
  • It will never silently redirect an existing username mapping to a different account.
  • It will never grant access to a username that does not resolve on GitHub.

This is why re-running a release is safe, and why a wrong username has to be corrected deliberately rather than automatically.
